# 控制平面

[English](../../architecture/control-planes.md) | 中文

数据平面做工作。控制平面决定工作是否、如何、在什么条件下可以发生。多数 Agent 失败
本质上是控制平面失败，只是看起来像模型失败。

## 数据平面 vs 控制平面

| 数据平面 | 控制平面 |
| --- | --- |
| 执行工具与流程 | 决定身份、策略、能力、协调 |
| 处理载荷与状态 | 处理权限、约束与证据 |
| 随工作量扩展 | 随决策与治理扩展 |
| 失败表现为错误 | 失败表现为未授权或未治理行动 |

数据平面强、控制平面弱的系统可以很快、很有能力，但不可治理。

## 五个控制平面

| 平面 | 问题 | AxisVela 示例 |
| --- | --- | --- |
| **身份** | 谁在行动，能否证明？ | EIDOVELA、NOMIVELA |
| **策略** | 允许什么，谁批准？ | AEGIVELA、SYMBIVELA |
| **能力** | 可以调用什么，如何治理？ | MODUREGIS、ORCHADYN |
| **协调** | 谁在做什么，状态如何？ | Harmovela、COORDIVELA |
| **保障** | 我们怎么知道它仍然有效？ | TEKMOVELA、PEIRAVELA、SYNDOVELA |

这些平面相关但不可互换。有效身份不蕴含授权；能力目录不蕴含协调；测试通过不蕴含
行动被正确授权。

## 平面如何交互

一条有用的请求路径：

1. **身份**建立 Agent 与工作负载。
2. **能力**解析 Agent 想调用的东西。
3. **策略**在当前上下文中授权调用。
4. **协调**确保没有冲突工作，并有明确所有者。
5. **执行**发生在数据平面。
6. **保障**检查结果并记录证据。

顺序可以变化，但决定必须显式。

## 设计规则

- **不要把控制放进提示词。** 提示词是上下文，不是执行。
- **保持平面可分离。** 团队应能在不重写运行时的情况下改变策略。
- **让决定可观测。** 每个平面都应发出决定记录。
- **高风险行动失败关闭。** 控制平面不可用时，对重大行动的安全默认是拒绝。
- **跨平面使用同一身份。** 否则归因会断裂。
- **限制委托。** 权限在 Agent 间应衰减，而不是放大。
- **分开开发协调与运行时协调。** 它们的状态与失败模式不同。

## 最小实现

你不必从五个平面开始。一个实用顺序：

1. 身份 + 策略钩子（默认拒绝）。
2. 能力列表 + 沙箱。
3. 效果账本 + 追踪。
4. 高风险行动审批。
5. 出现多 Agent 或长期工作时加协调。
6. 变更需要证据时加保障。

这个顺序让控制平面与风险成比例。

## 要点

- 控制平面是治理的架构。
- 每个平面回答不同问题；把它们混在一起会产生盲区。
- 如果决定没有被记录，它就不是控制平面，而是希望。
