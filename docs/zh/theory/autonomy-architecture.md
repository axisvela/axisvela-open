> 自主性不是没有控制，而是在架构边界下修改自身控制结构的能力。

## 一个实用的自主性阶梯

以下阶梯是**为设计讨论做的综合**，不是所引论文的标准。它有助于选择控制。

| 级别 | 系统可以做什么 | 最低控制 |
| --- | --- | --- |
| **辅助** | 建议行动，由人执行 | 评审、日志 |
| **监督** | 执行低风险步骤，高风险需人审批 | 策略、审批、证据 |
| **委托** | 在委托权限下执行受限任务 | 身份、范围衰减、撤销 |
| **有界自治** | 在定义好的包络内规划与执行 | 沙箱、预算、恢复、审计 |
| **元控制** | 在架构内修改自身策略、能力或计划 | 变更控制、职责分离、重新验证 |

多数企业系统应先追求监督或委托级自主性。只有在包络被强制执行时才适合有界自治。
元控制是一种治理能力，不是默认开启的功能。

## 架构作为法则

核心主张是：架构是构成性的。它决定哪些配置可能、哪些控制可执行、哪些证据可产生。
没有架构规格的系统不只是不完整；它在原则上不可治理。

直接的设计结论：

- 不能在架构边界执行的政策，只是建议。
- 没有连接到执行路径的审批，只是表演。
- 不是由架构产生的证据主张，只是叙事。

## 人类主权

自主性受人类以下权利与能力约束：

- 知道 Agent 即将做什么；
- 批准、拒绝或修改高风险行动；
- 在执行中介入；
- 撤销权限；
- 事后检查证据；
- 修改授予自主性的架构。

这些不是 UX 功能，而是控制平面要求。

## 检查清单

提高自主性前，问：

1. 包络是什么，在哪里执行？
2. Agent 可以改变自己的什么？
3. 谁能撤销权限，多快？
4. 什么证据证明包络成立？
5. Agent 出错时会发生什么？
6. 人类能否不停止整个系统而介入？
7. 新自主性级别是否经过验证与仿真？

如果这些问题没有架构层面的答案，自主性级别还没有准备好。
